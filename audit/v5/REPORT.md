## Протокол и воспроизводимость

Сначала непосредственно через GitHub прочитаны базовые `TASK.md`, все четыре модифицированных файла пяти кандидатов и перечень исходных тестов; отдельно проверено сравнение каждого HEAD с общей базой. Затем добавлены **8 прицельных наблюдательных проб**: два контроля (приватность и одновременный bookmark CAS), пять различающих диагностик и одна дополнительная проверка safe-integer.

- [Независимые пробы](probes.mjs) выполняют реальный код кандидата, не модифицируя исходники.
- [Отдельный workflow](../../.github/workflows/v5-audit.yml) использует matrix и SHA-pinned checkout пяти кандидатов; `git rev-parse HEAD` сверяется с полным эталонным SHA.
- [Успешный Actions run #40263595773](https://github.com/lolokeksu09/Skill-Benchmark-Lab/actions/runs/40263595773) выполнил исправленную версию `probes.mjs` на всех пяти точных SHA; все jobs успешны, Node `v22.23.3`. В контроле bookmark CAS отправляются два перекрывающихся аутентифицированных HTTP PUT через `startServer()` — не прямые последовательные вызовы синхронного `engine.bookmark()`.
- [Сохранённые JSON-доказательства](evidence.json) содержат фактические ответы, SHA, идентификаторы jobs и исходный workflow run. Сырые ответы доступны также в журналах по маркеру `V5_OBSERVATIONS`.

**Примечание:** зелёные jobs — это успешное выполнение скрипта наблюдений, **не прохождение кандидатом критериев**. Клиентские пробы запускают реальный `web/app.mjs` в Node VM с управляемыми `document` и `fetch`. Это изоляционная fault-injection проверка логики, **не Chromium E2E**. Существующие 33 Node и 11 Chromium тестов V4 не менялись и не перезапускались.

| Два PUT с одной версией → 200, 412 | OK | OK | OK | OK | OK |
| Сконструированная несуществующая позиция курсора → 400 | **200** | 400 | 400 | **200** | **200** |
| Нет авторизации, JSON некорректен → 401 | **400** | 401 | 401 | 401 | **400** |
| Два быстрых Load more: запросы / новые одинаковые карточки → 1/1 | **2/2** | 1/1 | 1/1 | 1/1 | **2/1** |
| HTTP 200 с неверными типами bookmark → корректный rollback | **нет** | да | да | **нет** | **нет** |
| HTTP 200 с чужим bookmark id → отказ, rollback | **нет** | да | **нет** | **нет** | **нет** |
| If-Match за пределами safe integer → 400 (дополнительная политика) | 400 | 412 | 400 | 412 | 412 |

Для fault injection с `saved:'invalid', version:'bad'` клиенты A/D/E сохраняют некорректное состояние: `aria-pressed` становится `invalid` или `true`, следующий запрос уходит с `If-Match: "bad"` и сообщение об ошибке отсутствует. B/C восстанавливают `aria-pressed=false`, версию `0`, следующий `If-Match: "0"` и показывают ошибку.

Для fault injection с ответным `id:'wrong-post'` только B отвергает успешный ответ и сохраняет исходную версию. A/C/D/E принимают результат и на следующем PUT используют `If-Match: "1"`. **Штатный сервер не наблюдался выдающим такой ответ**; речь о доказанной реакции клиента на искусственно подставленный ответ.

Для курсоров применена одна семантика «несуществующая позиция», но соответствующие кодировки: у A/C/D/E установлен `offset=1000000` на основе действительного курсора, а у B — отсутствующий anchor `id` с пересчитанной HMAC-подписью по открытому в source ключу. Это не одинаковые байты и не тест криптографической стойкости.

## Существенные различия и риски без подтверждённого нарушения V4

- **A:** корректны приватность, CAS, строгие limit/If-Match и безопасный DOM; offset без верхней границы, повторные Load more не защищены от конкуренции и нет проверки положительного JSON-ответа.
- **B:** keyset-курсор по `createdAt,id` и HMAC, поиск anchor, блокирование in-flight Load more, проверки формы feed и `body.id/saved/version`. Механизм сложнее, но качество измеряется наблюдаемой устойчивостью, а не эстетикой. HMAC-ключ [зашит в исходники](https://github.com/lolokeksu09/Skill-Benchmark-Lab/blob/9239a91ccb1776a21834ba6167c9672b838bac68/src/engine.mjs#L40-L58), поэтому подпись **не является секретной защитой** от подделки клиентом. В рамках local-only fixture это не обнаруженная брешь в авторизации.
- **C:** offset с явной проверкой `offset > visible.length`, безопасный разбор If-Match, serial на каждом запросе, отключение More во время загрузки, валидация типов JSON. Но отсутствует проверка ответного bookmark `id`. Для статичных seed-posts offset корректен; реальная пагинация при одновременных вставках в массив не исследована.
- **D:** AbortController + generation и блокировка повторного Load more работают, но нет границы курсора и проверки возвращённого bookmark `id/version` при HTTP 200.
- **E:** serial предотвращает повторную отрисовку старого Load more, но второй GET всё равно отправляется; курсоры вне диапазона и malformed bookmark-ответы некорректно обрабатываются, а анонимный invalid JSON даёт 400.

Дополнительная проверка If-Match `"9007199254740993"` показала 400 у A/C и 412 у B/D/E. Во всех случаях изменения bookmark нет. **Не начисляем штраф за 412**: исходный V4-контракт явно не устанавливал, что всякая синтаксически цифровая, но небезопасно большая версия должна отклоняться именно с 400. Это реальное расхождение в строгости валидации, а не доказанная эксплуатационная уязвимость.

У всех кандидатов унаследовано чтение JSON тела без явного size limit и хранение bookmark в process-local `Map`. Устойчивость к крупным телам, перезапускам и многопроцессному CAS не доказана, но эти условия выходят за рамки локального benchmark. Демо-токены публичны **по дизайну** и не должны применяться в production.

**XSS, приватность и accessibility:** все кандидаты используют текстовые DOM API вместо опасного `innerHTML` для заголовков/описаний; у всех присутствуют aria-pressed/подписи/focus-visible и адаптивные стили. Ранее успешный Chromium V4 охватывает 375px, клавиатуру, сбой сохранения и гонку поиска. В V5 **не проверялись** 320px, screen reader, реальное touch-устройство, новая нагрузка или внезапные сбои браузера, поэтому не выдаются неподтверждённые оценки по этим направлениям.

## Прозрачный итог по наблюдаемому качеству

**Пять бинарных критериев**: корректно отвергнуть несуществующий курсор; приоритет 401 для анонимного API; не выполнять повторный Load more; откатить неверные типы HTTP 200 bookmark; откатить HTTP 200 bookmark с чужим id. Каждый критерий считается один раз, даже если включает несколько симптомов. Два контрольных сценария пройдены всеми и не меняют различающий счёт. За строки кода, коммиты, CI-секунды, визуальную «красоту» или сложность начислений нет.

| Подход | Контроли | 5 дополнительных критериев | Что следует из результата |
|---|---:|---:|---|
| Control | 2/2 | 0/5 | Есть подтверждённые граничные дефекты |
| P2P Original | 2/2 | **5/5** | Наиболее устойчив **в данной выборке** |
| P2P Improved | 2/2 | **4/5** | Пропускает несовпадение bookmark id |
| DDS | 2/2 | 2/5 | Защищён от двойного Load more, но есть другие граничные дефекты |
| Combined | 2/2 | 0/5 | Не дублирует DOM-карточки, однако делает лишний GET и допускает другие дефекты |

**Вывод:** на этих проверках P2P Original лидирует; P2P Improved близок и строже в тесте огромной версии If-Match. Это **не основание** называть метод лучшим в целом: отсутствуют независимые повторы, разные задания, слепая оценка, production-тесты, измерение времени генерации и токенов. Критерии включают искусственно повреждённые успешные ответы и имеют разный практический вес; отличие 5/5 от 4/5 не является статистическим доказательством превосходства.

Ни один из V5-сценариев не продемонстрировал XSS, утечку private-записей или два успешных конкурентных bookmark PUT с одной версией. Это **ограниченное отрицательное наблюдение**, не подтверждение отсутствия любых уязвимостей.
