## Краткий вывод

V5 успешно обнаружил поведенческие различия, пропущенные исходным набором 44/44. Но итог `5/5` у P2P Original означает только победу по пяти заранее выбранным дополнительным критериям. Это не общий рейтинг качества модели или метода.

**Решение для V6:** использовать P2P Original как предварительный поведенческий reference, но не как исходную ветку для остальных вариантов. Все подходы должны стартовать из одного нового замороженного baseline и получать одну и ту же спецификацию. Результаты качества, защитной обработки, времени и usage-токенов нужно показывать раздельно.

## 2. Ограничения методики V5

1. **Разные классы ошибок сведены в один бинарный счёт.** Ошибка авторизации, лишний запрос и отказ обработать искусственно повреждённый успешный ответ не имеют одинаковой тяжести. Счёт 5/5 полезен только как сводка выбранных критериев.
2. **Критерий курсора нуждается в точной формулировке.** Для offset-кандидатов проверяется валидно закодированное значение за концом списка; для keyset-кандидата — корректно подписанный токен с отсутствующим anchor. В V6 нужно заранее определить, какие невозможные позиции обязаны давать 400.
3. **UI fault injection выполняется в Node VM с подменённым DOM/fetch.** Это полезная изолированная проверка логики, но не Chromium E2E. Нельзя делать выводы о полном поведении реального браузера только по ней.
4. **Проверка CAS теперь проходит через HTTP, но не является многопроцессным стресс-тестом.** Движок работает синхронно внутри одного Node-процесса; текущая проверка подтверждает контракт двух запросов с одной версией, но не устойчивость распределённого хранилища.
5. **Не проверена ошибка un-save при исходном `saved=true`.** V5 fault injection начинает с `saved=false`; V4 требует восстановления точного предыдущего состояния, включая ранее сохранённую запись.
6. **Не проверена пагинация при изменении набора записей между страницами.** Текущая fixture не предоставляет API добавления/удаления постов. V6 должен либо добавить общий контролируемый тестовый seam в новый baseline, либо явно оставить этот случай вне scope — нельзя притворяться, что статический обход доказывает устойчивость к вставкам.
7. **Нет независимых повторов и статистического основания для общего рейтинга.** Пять реализаций прогнаны на одной задаче и одном наборе seed-данных. Нельзя заявлять статистическую значимость или универсальное превосходство.
8. **Фактические токены и время генерации не доступны в сохранённых данных V5.** Время GitHub Actions — это время CI, а не время написания решения. Размер diff или оценка токенизатора не заменяют фактический usage.

## 3. Решение по выбору reference

**P2P Original — предварительный reference по наблюдаемому поведению V5**, поскольку он прошёл все пять различающих критериев. P2P Improved остаётся близким вариантом, но в одном fault-injection сценарии принимает bookmark-ответ с чужим ID.

Это решение не означает:
- что P2P Original нужно merge;
- что его код нужно копировать в другие варианты;
- что метод в целом лучше DDS или Combined;
- что найденные различия обязательно имеют одинаковую практическую значимость.

Для V6 сохраняются общий baseline и одинаковая задача для всех подходов. P2P Original используется только как дополнительная контрольная реализация/reference, а не как база остальных веток.

## 4. Что должно изменить V6

- Пререгистрировать ожидаемые результаты и классификацию до запуска кандидатов.
- Разделить **контрактные проверки** и **defense-in-depth/fault-injection**; не смешивать их в одном непрозрачном балле.
- Использовать реальные HTTP-границы для API, настоящий Chromium для браузерных сценариев и VM только как дополнительный инструмент.
- Добавить rollback из исходного `saved=true`, повторную попытку с правильным ETag, ошибки сети/JSON, malformed ID и проверку, что сервер после ошибки продолжает отвечать.
- Добавить точные случаи границы курсора и полный обход страниц; тест на динамические вставки запускать только при наличии общего детерминированного test seam в новом baseline.
- Сохранить неизменяемые SHA кандидатов и сырые результаты каждого сценария.
- Вести отдельный ledger для времени генерации, времени CI и usage-токенов. Значения брать только из подтверждённых источников; недоступное записывать как `null` с причиной, не вычислять «фактические токены» из размера текста.
- Для качества использовать таблицу по критериям и уровни серьёзности; не объявлять глобального победителя на основании одного суммарного счёта.

## 5. Scope и целостность

Ревью не изменяет код пяти кандидатов, V4 tests, TASK.md или baseline. PR #21–#25 остаются отдельными и не объединёнными. PR #26 открыт, merge не выполнен.
