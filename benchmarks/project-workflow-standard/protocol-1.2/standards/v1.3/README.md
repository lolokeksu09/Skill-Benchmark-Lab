# Стандарт ведения проектов — 1.3

Порядок работы, выверенный на WrCommunity и обобщённый для других проектов. Стек, команды, хостинг, устройства и разрешения определяются конкретной задачей. Комплект содержит 9 документов и не требует плагина.

## Что читать

| Файл | Назначение | Когда |
|---|---|---|
| [AGENTS.md](AGENTS.md) | Общие правила и границы самостоятельности | В области действия инструкции |
| [PROJECT.md](PROJECT.md) | Решения владельца и ссылки на источники | Первый вход и изменение особенностей |
| [TESTING-LEVELS.md](TESTING-LEVELS.md) | L1–L5 и критерии результата | Проверки, CI, поставка |
| [templates/PLAN.md](templates/PLAN.md) | План зависимых этапов | Крупная или рискованная задача |
| [templates/CONTINUATION.md](templates/CONTINUATION.md) | Один текущий снимок | Передача или остановка многоэтапной работы |
| [templates/AUDIT.md](templates/AUDIT.md) | Проверяемые находки | Заказанный аудит |
| [templates/VERIFICATION.md](templates/VERIFICATION.md) | Запись доказательств | Нужен отдельный отчёт |
| [templates/RELEASE.md](templates/RELEASE.md) | Кандидат и результат поставки | Разрешённый выпуск |

Шаблоны не являются активными задачами или результатами тестов. Используй существующие документы; при необходимости копируй только нужный шаблон и исправляй относительные ссылки. Для небольшой задачи достаточно записи в задаче/PR.

## Подключение нового проекта

1. Размести комплект в корне новой рабочей директории. Этот README — руководство комплекта: при появлении продуктового README перенеси руководство под другим именем, сохранив ссылки.
2. Передай идею, ограничения и ожидаемый результат. Агент определяет цель и критерий первой работающей поставки, затем заполняет подтверждённые решения в PROJECT.md.
3. Если стек ещё не выбран, агент предлагает подходящий вариант с причинами. Выбор не должен навязываться стандартом. Существенные открытые решения уточняются; независимая работа продолжается.
4. Запуск, сборка, тесты и CI создаются по реальной задаче. Распаковка архива сама по себе их не настраивает и не доказывает готовность продукта.

## Подключение существующего проекта

1. Сначала прочитай действующие инструкции, документацию, конфигурацию и Git diff.
2. Сравни правила и совмести их с действующими инструкциями, сохранив пользовательские изменения. Если корневой AGENTS.md уже есть, сохрани его правила и добавь применимые положения комплекта либо ссылку на него, только если среда поддерживает такой способ подключения. Размещение AGENTS.md во вложенной папке само по себе не делает его правила действующими на весь проект. Проверь область действия, фактическое подключение в используемой среде и относительные ссылки. Если автоматическое подключение не подтверждено, явно передай нужные инструкции агенту и отметь ограничение. README и другие пользовательские файлы не перезаписывай автоматически.
3. Сохрани принятый стек, запреты, обязательные проверки и определения уровней. При несовпадении L-уровней запиши соответствие вместо переименования jobs.
4. PROJECT.md хранит только нужные решения и указатели. Секреты, копии манифестов и меняющиеся статусы CI сюда не переносятся. Начни с текущей задачи; не перестраивай проект ради структуры комплекта.

## Текст для нового чата

«Используй приложенный стандарт ведения проекта. Сначала прочитай AGENTS.md и PROJECT.md, сверь актуальный код и инструкции. Адаптируй профиль к моей задаче, сохрани действующие ограничения. Выполняй разрешённую работу самостоятельно, проверяй актуальную версию и оставляй краткую точку продолжения. Моя задача: …»

Если задача уже дана, используй её сразу. Для продолжения разработки передай актуальную рабочую точку продолжения: сам архив не содержит состояния конкретного проекта.

## Что изменено в 1.3

- Уточнено подключение комплекта к проекту с существующими инструкциями: сохранение правил, область действия, поддержка ссылок средой и проверка путей.
- Уточнён идентификатор выпуска для проекта без Git.
- UI-проверки выбираются по применимым состояниям; недоступные проверки указываются отдельно.
- Описана работа с ошибкой, которую пока невозможно воспроизвести: доказательства, гипотеза, границы исправления и неподтверждённая регрессия.

Проверки поведения агентов для изменений 1.3 в этом комплекте не заявлены. Результаты ниже относятся к предыдущим версиям.

## Что изменено в 1.2

- Каждое актуальное требование сверяется с результатом перед завершением. Частичное и заблокированное явно остаются в остатке; исключить требование может владелец.
- Разрешённая задача продолжается до результата или конкретного блокера; при блокировке одного пункта выполняются независимые части.
- Повтор сбоя требует основания. При неизвестном исходе записи сначала проверяется фактическое состояние; бесконечные одинаковые попытки не предписываются.
- Уточнение задачи обновляет объём, сохраняя остальные обязательства; отменённые пункты помечаются явно.
- Перед завершением раздельно сверяются реализация, проверка, сохранение и заказанная доставка.
- Добавлено разрешение существенных противоречий между требованиями, планом и конфигурацией. План, проверка, продолжение и выпуск ссылаются на единый реестр требований.

Для небольшой правки реестр и финальная сверка могут быть одной краткой записью; дополнительные документы не обязательны.

## История 1.1 относительно 1.0

- AGENTS.md сокращён; настройки и определения проверок вынесены к своим источникам.
- Отдельно описано подключение нового и существующего проекта.
- Добавлена таблица самостоятельности: обычные обратимые действия выполняются без лишних подтверждений; ранее данное разрешение сохраняет силу в своих границах.
- PROJECT.md хранит решения и ссылки, а не дублирует стек/команды/HEAD.
- CONTINUATION.md сводится к шести полям; история остаётся отдельно.
- Явно разделены техническая проверка документов и доказательство поведения модели.

## Прикладная проверка 1.2

27.10.2026 выполнены четыре свежих агентных запуска: две версии инструкций × два небольших изолированных Python CLI-проекта. Задания и начальные продуктовые файлы в паре одинаковы; различаются версии инструкций и пути. Агентам переданы только их проект и исходная задача, без ожидаемого решения и истории основного чата. Новые инструкции после получения результатов не корректировались; здесь добавлен только отчёт.

| Задание | v1.1 | v1.2 |
|---|---|---|
| CSV: BOM/пробелы/пустые строки, email-валидация, CLI limit, документация | 12/12 независимых проверок | 12/12 независимых проверок |
| JSON-отчёт: обязательные/необязательные статусы, сохранение пользовательского diff, отмена старого плана, документация | 13/13 независимых проверок | 13/13 независимых проверок |
| Реальный внешний сервис второго задания | Недоступно: код 2, адрес не предоставлен | Недоступно: код 2, адрес не предоставлен |

Независимый evaluator проверяет функции, CLI и отдельные свойства файлов/документации; он хранится отдельно от заданий. До исправлений исходные фикстуры дали 8 и 9 сбоев соответственно. Написанные агентами unit-наборы дополнительно повторно выполнены: все четыре успешны. Исходный пользовательский STATUS_LABEL и интеграционный скрипт сохранены в обеих версиях.

Ручная оценка FINAL.md: обе версии сообщают о результате и блокировке интеграции. В двух отчётах v1.2 есть явная таблица «требование → подтверждение/остаток»; v1.1 также охватывает требования, но оформляет их списками. В blocked обе версии обновили старый CSV-план на актуальную JSON-задачу. Это наблюдение, а не доказательство превосходства версии.

**Ограничения:** по одному запуску на сочетание версии и задания; общие инструкции среды сохранялись; точный идентификатор модели и стоимость не зафиксированы. Это небольшие искусственные проекты с исполняемым кодом, не production. Изолированный контрольный случай blocked не использовался для последующей настройки инструкций. Проверки неизвестного исхода записи/повторов, публикации, UI и полного жизненного цикла большого проекта не выполнялись агентами. Остальные 12 ситуаций выше остаются разбором текста. Разница качества, стабильность, экономия токенов и скорость разработки не установлены.

Задания, снимки обеих версий, начальные хеши, полученный код, отчёты, diff и результаты evaluator сохранены отдельным архивом Project-Workflow-Validation-v1.2.zip. Полных трасс инструментальных вызовов там нет. Основной комплект по-прежнему содержит только 9 документов.

Комплект не разрешает внешних действий сверх задачи и не заменяет инструкции эксплуатации проекта.
