# Пример 3 — кандидат, разрешение и доставка

> Полностью вымышленный процесс. Он демонстрирует разницу статусов, а **не настоящую публикацию, разрешение или тест**.

**Кандидат:** условная версия `2.1.0-rc1`; для проекта с Git — точный SHA выпуска, без Git — SHA-256 реально собранного файла. Условные требования `REQ-010` и `REQ-011` должны ссылаться на единый реестр, а не переписываться в RELEASE.md.

| Этап | Пример записи | Что разрешено заключить |
|---|---|---|
| L4 | Все обязательные jobs кандидата имеют точные ссылки на результаты и версию; незавершённые REQ отсутствуют | Кандидат прошёл установленную приёмку, **не опубликован** |
| Разрешение | Владелец явно разрешил выпуск только версии `2.1.0-rc1` в одну названную целевую среду | Можно выполнить поставку **только в указанном объёме** |
| Публикация | Зафиксирован фактический артефакт и журнал разрешённой операции | Публикация выполнена, **L5 ещё не подтверждён** |
| L5 | Сверена активная версия и выполнен основной сценарий именно доставленного кандидата | Поставка: «опубликовано и проверено» |

Если применяется исключение, итог L4 записывается как **«с исключениями: EXC-ID…»**, а не как «все проверки успешны». Фактический статус исходной проверки и остаточный риск сохраняются.

Если L5 не выполнен либо активная версия не совпала, **нельзя** писать «опубликовано и проверено» — нужен фактический статус и устранение причины.

**Исключение (при необходимости):** условный `EXC-004` относится только к конкретному обязательному gate и одному кандидату, фиксирует уполномоченного владельца, причину, остаточный риск, срок и компенсирующую проверку. Статус исходной проверки остаётся «недоступно»/«не выполнено» по факту, а gate — «закрыт по EXC-004» только в разрешённом охвате. Ни наличие EXC, ни L4 не заменяют самостоятельное разрешение на публикацию. Истечение срока требует нового решения.
