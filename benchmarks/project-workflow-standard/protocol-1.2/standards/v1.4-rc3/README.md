# Project Workflow Standard — 1.4-rc3

Универсальный стандарт работы над проектом с ИИ-агентом: границы самостоятельности, требования, проверка по риску и доказуемая поставка. **RC — кандидат на выпуск, не подтверждённое улучшение относительно v1.3.** Не задаёт стек, команды, платформу или разрешения для конкретного проекта.

## Подключение и использование

| Документ | Назначение | Когда читать |
|---|---|---|
| [AGENTS.md](AGENTS.md) | Обязательные правила и разрешения | При работе агента в его области действия |
| [PROJECT.md](PROJECT.md) | Решения владельца и ссылки на реальные источники | На входе в проект / при изменении решений |
| [TESTING-LEVELS.md](TESTING-LEVELS.md) | L1–L5, статусы, доказательства, исключения | Перед выбором проверок, merge и поставкой |
| [templates/PLAN.md](templates/PLAN.md) | Один реестр требований и зависимых этапов | При сложной или многоэтапной работе |
| [templates/CONTINUATION.md](templates/CONTINUATION.md) | Текущая точка продолжения | При прерывании/передаче длительной задачи |
| [templates/AUDIT.md](templates/AUDIT.md) | Проверяемые находки | При заказанном аудите |
| [templates/VERIFICATION.md](templates/VERIFICATION.md) | Подробные результаты приёмки | Если нужен отдельный отчёт |
| [templates/RELEASE.md](templates/RELEASE.md) | Кандидат, разрешение, результат поставки | При разрешённой поставке |

[CHANGELOG.md](CHANGELOG.md) содержит изменения версий; [VALIDATION.md](VALIDATION.md) — ограничения подтверждений и план независимых тестов. Три **вымышленных учебных** примера находятся в [examples/](examples/README.md). Необязательная статическая самопроверка: `python tools/check_standard.py .` (или передай путь к ZIP); она не проверяет поведение агента.

## Два режима ведения документации

- **Light:** небольшая локальная задача — достаточно записи в задаче/PR или краткого результата; без обязательного отдельного плана, REQ-ID и отчёта. Применимые обязательные проверки всё равно выполняются.
- **Full:** сложный объём, зависимые этапы или длительная работа — один реестр с устойчивыми REQ-ID, план/точка продолжения при необходимости, доказательства с привязкой к требованиям. Не требуется создавать Issue/PR, если проект их не использует.

**Режим документации и строгость проверки независимы.** Маленькая правка авторизации требует негативных сценариев; большая редактура документации не требует искусственного L4/L5. Проверки выбираются по риску и существующим обязательным gates проекта, см. [алгоритм](TESTING-LEVELS.md).

## Новый проект

1. Размести комплект в корне рабочей области; проверь относительные ссылки и реально действующие инструкции. Размещай три основных файла (`AGENTS.md`, `PROJECT.md`, `TESTING-LEVELS.md`) вместе, даже если при Light шаблоны не читаются. Если используется сокращённая установка, сохрани доступность нормативных правил и работоспособность ссылок либо явно передай недостающие инструкции агенту.
2. Передай цель, ограничения и результат первой работающей поставки. Заполняй в `PROJECT.md` только подтверждённые решения и ссылки на текущую документацию.
3. При отсутствии стека выбери подходящий по требованиям, не по содержимому этого стандарта. Реальные команды сборки, тестов и платформенные особенности определяет проект.

## Существующий проект

1. Сначала прочитай действующие инструкции, структуру, конфигурацию, Git HEAD/diff (либо версию/хеш без Git). Не перезаписывай пользовательские файлы.
2. Если корневой `AGENTS.md` уже есть, **совмести** применимые правила, не замещай действующие ограничения. Вложенные `AGENTS.md` действуют только в области, установленной средой; одна ссылка или перемещение файла не гарантируют автозагрузку инструкций. Проверь поддерживаемый механизм и пути; если он не работает — передай инструкции явно.
3. Сохрани стек, действующие gates, местные определения L-уровней, контракты и способы поставки. При различии определений укажи соответствие вместо переименования чужих проверок. Начинай с текущей задачи, не перестраивая проект ради этого комплекта.

## Короткая последовательность работы

Цель и ограничения → критерии готовности → локальная реализация/изолированные PR при необходимости → проверки с доказательствами → сохранение → **только разрешённая** поставка → проверка доставленной версии. При блокировке закончи независимые части, а остаток назови явно. Никакая запись о выпуске не является разрешением опубликовать его.

## Глоссарий

- **Владелец:** лицо, принимающее продуктовые решения и дающее разрешения в своих полномочиях.
- **Агент:** исполнитель, действующий в пределах задач и инструкций среды.
- **Среда исполнения:** где агент работает и какие инструменты доступны; **целевая среда:** где используется результат; **инструкции среды:** правила доступа и приоритета, которые не заменяет этот комплект.
- **Gate:** обязательная для заданного изменения проверка или условие; skipped/pending не означает успех. **Исключение:** явно разрешённый ограниченный обход gate, но не результат теста.
- **Доказательство:** наблюдаемый результат конкретной версии и сценария. **Артефакт:** идентифицируемый результат сборки/документ. **Доставка:** фактическая передача или публикация согласно разрешению, не синоним готовности локально.

## Текст для нового чата

> Используй приложенный Project Workflow Standard. Прочитай действующие инструкции, AGENTS.md и PROJECT.md, сверь актуальные файлы и ограничения. Для задач выбери Light или Full по объёму документации; проверки определи отдельно по риску и обязательным gates. Сохраняй чужие изменения, работай самостоятельно в разрешённых границах, не подменяй результаты проверок, дай проверяемый результат и остаток. Задача: …

Шаблоны — **не активные задачи и не готовые отчёты**. При переносе копии поправь относительные ссылки, не создавай второй источник истины. Основной комплект не требует плагина и не даёт дополнительных разрешений на внешние действия.
