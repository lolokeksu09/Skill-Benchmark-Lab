# Уровни проверок L1–L5

Редакция комплекта: **1.4-rc3** (определения L1–L5 уточнены, исходная схема сохранена). Объём проверки выбирается по риску и обязательным правилам проекта. Это внутреннее соглашение, не отраслевой стандарт и не привязка к платформе.

## Уровни

| Уровень | Назначение | Достаточное подтверждение |
|---|---|---|
| **L1 — базовая корректность** | Простые ошибки исходников, конфигурации или текста | Применимые типы/линтер/синтаксис либо факты/ссылки проверены |
| **L2 — затронутая область** | Изменённое поведение модуля или компонента | Ожидаемое поведение и существенный отказ проверены; для исправления исходный сбой воспроизведён либо ограничение воспроизведения явно зафиксировано, а целевая регрессионная проверка выполнена на исправленной версии |
| **L3 — связанные сценарии** | Взаимодействие модулей и границы доверия | Сквозной сценарий и рискованные границы проверены в представительном изолированном окружении |
| **L4 — полная приёмка** | Готовность кандидата | Все обязательные gates закрыты успешными проверками либо применимыми активными исключениями; фактические статусы проверок и EXC-ID сохранены; артефакт известен |
| **L5 — проверка поставки** | Работа доставленной версии | Подтверждены фактическая версия в целевой среде, запуск/здоровье и основной сценарий |

Для библиотеки L5 может быть установкой пакета в контрольный проект, для приложения — установкой и запуском, для сервиса — проверкой разрешённого развёртывания. Сам номер уровня не доказывает покрытие.

Если исходный сбой не удалось воспроизвести, успешная проверка исправленной версии подтверждает лишь проверенное поведение, **не** доказывает устранение исторической причины. Сохрани ограничение и необходимую оставшуюся проверку в итоге.

При записи L4 отдельно указывай **«без исключений»** либо **«с исключениями: EXC-ID…»**. Второй вариант не означает успешность пропущенной проверки, сохраняет её остаточный риск и не заменяет отдельное разрешение на поставку.

## Выбор

| Изменение | Обычный объём |
|---|---|
| Документация | Применимые L1; исполнение изменённой команды, если оно необходимо и среда доступна |
| Косметика | Применимые L1, целевой просмотр новой сборки как L2; без искусственного набора unit-тестов |
| Ошибка/поведение модуля | L1 + целевые L2 |
| API-контракт или пользовательский путь | L1 + целевые L2/L3 |
| Авторизация, приватность, деньги, данные, совместимость, конкуренция | Положительные и отрицательные L2/L3 независимо от размера diff; для миграции — восстановление |
| Сборка/CI | Применимые L1 и фактический запуск изменённого процесса; L3 при межсистемной границе |
| Merge/выпуск | L4 по принятой политике, затем L5 для разрешённой поставки |

### Короткий алгоритм выбора

1. Сначала установи **обязательные проверки проекта**: они не отменяются режимом Light или размером diff.
2. Для текста и конфигурации выполни применимые L1; для поведения добавь целевые L2, включая значимый сценарий отказа.
3. При взаимодействии компонентов, внешнем сервисе или границе доверия добавь L3; для авторизации, приватности, денег, данных и совместимости проверь позитивный и негативный пути, а при риске потери данных — восстановление.
4. Для пользовательского интерфейса проверь **актуально запущенную** изменённую версию и действия пользователя в представительном окружении. Охват (устройство/эмулятор, реальные/подставные зависимости) запиши раздельно.
5. Для кандидата на разрешённый merge/release выполни L4 по действующей политике; после **разрешённой** поставки — L5 на реально доставленной версии.
6. Если применимая проверка недоступна, зафиксируй причину и остаточный риск. Это не успешная проверка.

**Light/Full определяют объём записей, не строгость проверок.** Все пять уровней после каждой правки не нужны. Расширяй объём при новом риске, сбое или непроверенной зависимости. Отсутствующий обязательный тест обозначай пробелом; не выдумывай исполнение или команды.

## Сопоставление с проектом

Сохраняй существующие имена и определения L-уровней. Если они отличаются, запиши соответствие. FULL может означать L4; RELEASE — объединять L4, доставку и L5. Название job само по себе не доказывает её охват.

В существующей документации для используемых уровней укажи команду/CI-job или воспроизводимую ручную процедуру, охват/платформы, окружение, критерий успеха и условие обязательности. На точные команды ссылайся через конфигурацию, не дублируй её без необходимости.

## Справочник независимых статусов

Эти наборы **не объединяются в универсальный статус**. Например, успешная L2 не означает выполнения всего REQ; подготовленный выпуск не означает поставку.

| Объект | Допустимые состояния | Что это означает |
|---|---|---|
| Требование | Не оценено / в работе / выполнено / частично / заблокировано / исключено владельцем | Готовность конкретного критерия; исключение требует решения владельца |
| Проверка | Не выполнено / успех / сбой / недоступно / не применимо | Результат конкретного запуска; skipped, pending, cancelled без результата — не выполнено; N/A обосновать |
| Этап | Не начат / в работе / завершён / заблокирован / отменён | Состояние плана, не доказательство теста или поставки |
| Исключение | Активно / истекло / закрыто | Действительность разового разрешённого обхода конкретного gate, **не** результат проверки |
| Поставка | Подготовлено / опубликовано и проверено / поставка неуспешна / требуется восстановление | Только наблюдаемый статус доставки, отдельно от готовности кандидата |

## Статус и доказательства

- Различай **успех**, **сбой**, **не выполнено**, **недоступно**, **не применимо**; последнее обоснуй. Обязательная job в pending/skipped/cancelled/failure или без результата не закрывает gate.
- При сбое или недоступности обязательной проверки готовность блокируется до исправления либо применимого явно разрешённого исключения. Владелец не отменяет ограничений среды; исключение фиксируется как исключение, а не успех.
- Переиспользуй успешный результат только для относящихся к нему неизменных исходников, зависимостей, конфигурации, данных и окружения. Для exact-SHA gate требуется указанный SHA. L4 может включать подходящие результаты L1–L3 без повторного выполнения.
- Запись результата: ревизия и diff либо версия/**SHA-256 артефакта** без Git; среда и режим сборки; команда/действия; результат; **точный адрес соответствующего запуска, строки лога или снимка**; оставшиеся ограничения. Общая ссылка на главную CI или каталог без связи с результатом недостаточна.
- List, dry-run, план и написанный тест не подтверждают запуск. Подставной ответ проверяет лишь соответствующий участок; для реальной интеграции нужна реальная зависимость.
- Сборка не подтверждает просмотр интерфейса; эмулятор — физическое устройство; лабораторный замер — production-метрики. Сравнение скорости требует сопоставимых сборок, условий и выборки.
- При отсутствии среды продолжай доступную независимую работу, укажи причину, альтернативу и риск. Недоступность не считать успехом.
- Для каждого актуального требования проверь, что доказательство относится к его критерию готовности, пользовательскому сценарию и проверенной версии. В сложной задаче используй устойчивый REQ-ID в едином реестре, плане и отчётах; не копируй реестр в каждый документ. Успех других тестов не закрывает непроверенное требование; общий итог должен сохранять его остаток.
- Перед сохранением или передачей доказательств удаляй секреты, токены и приватные/персональные данные; для приватного доказательства оставляй безопасную ссылку с контролем доступа. Не публикуй исходные данные и не заменяй редактированием подлинный результат.

## Исключения из обязательных проверок

Обход обязательного gate допустим **только** при явном разрешении уполномоченного лица, в границах действующей политики проекта. Нельзя трактовать молчание, статус skipped, неудачу или недоступность как разрешение. Исключение не отменяет запретов среды, требований безопасности и отдельно необходимого разрешения на публикацию.

Для каждого исключения заведи короткую запись в действующем плане, задаче либо выпуске; **отдельный файл не обязателен**:

| Поле | Правило |
|---|---|
| ID | Устойчивый `EXC-001`, не повторно используемый для другого исключения |
| Gate/проверка и охват | Что конкретно пропущено; требование, версия/ревизия, среда и кандидат, если применимо |
| Причина и риск | Почему запуск невозможен/необязателен по решению владельца; остаточный риск |
| Разрешивший и источник | Кто уполномочен, где зафиксировано решение; агент не выдаёт себе разрешение |
| Временные границы | Срок/событие истечения и конкретная ревизия/выпуск; неизвестный срок не считать бессрочным |
| Компенсирующая мера | Альтернативная проверка и её реальные результаты либо явное отсутствие |
| Закрытие | Состояние: активно / истекло / закрыто; условие снятия исключения и необходимая перепроверка |

При выходе за охват, окончании срока или смене ревизии/выпуска исключение **не переносится автоматически** — нужно новое решение. Истёкшее/закрытое исключение не закрывает gate. Gate с применимым активным исключением помечай «закрыт по EXC-ID», но исходный тест оставляй «не выполнено»/«недоступно»/«сбой» по факту, а не «успех». Для значимого риска, не допускающего исключений по политике, gate остаётся блокирующим.

## Поставка

L4 не даёт разрешения на публикацию. Объём разрешения регулирует [AGENTS.md](AGENTS.md); для записи кандидата и результата используй [шаблон выпуска](templates/RELEASE.md) при необходимости. L5 подтверждает конкретный доставленный артефакт, а не только прошедший pipeline. Операции с production-данными и восстановление должны входить в согласованную процедуру.
