## Подтверждённые дефекты

### IND-01 — P1: оптимизация Python отключает обязательные проверки checker

Источник: `tools/check_standard.py:71`, `:76`, `:105`, `:113–143`.

Условие: `python -O tools/check_standard.py <package>` либо окружение `PYTHONOPTIMIZE=1`. В Python assert удаляется при оптимизации, поэтому на assert нельзя строить валидацию внешних данных.

Воспроизведение: во временной копии README.md заменён пустым файлом. Обычный запуск: exit 1, `Result: 6/8 checks passed`. Тот же вход с `-O`: exit 0, `Result: 8/8 checks passed`. Исходный комплект даёт 8/8 без оптимизации.

Влияние: автоматизация может молча принять повреждённый нормативный документ при штатном параметре интерпретатора. Это подтверждённый ложный успех утилиты; не доказательство того, что реальный релиз уже был ошибочно принят.

Минимальное исправление: явные условные проверки с собственным исключением/ненулевым exit, одинаковая отрицательная приёмка в обычном и оптимизированном режимах.

### IND-02 — P2: каталог читается вне корня через symlink

Источник: `tools/check_standard.py:44–46`.

Условие: в проверяемом каталоге есть ссылка на обычный файл вне каталога. `Path.is_file()` и `read_bytes()` следуют ссылке.

Воспроизведение: создан внешний файл с публичным тестовым sentinel, внутри копии создан `outside.bin` → этот файл. `load()` вернул внешний sentinel как содержимое `outside.bin`; полный checker выдал 8/8 PASS, exit 0.

Влияние: заявленная область чтения не ограничена корнем пакета. Содержимое попадает в память процесса; в выполненном опыте не было секретов, публикации содержимого или записи по ссылке. Чтение symlink-данных не равняется доказанной утечке.

Минимальное исправление: отклонять ссылки и специальные файлы; проверять все компоненты пути, использовать ограниченное безопасное чтение. При невозможности безопасного чтения отказывать с причиной.

### IND-03 — P2: переносимость и типы ZIP-путей не проверяются

Источник: `tools/check_standard.py:36–43`.

Условие: дополнительные ZIP entries с обратной косой чертой, неканоническими именами или UNIX symlink type.

Воспроизведение: три отдельных архива, каждый с исходными 16 файлами и одним дополнительным entry: `..\\outside.bin`; `alias//file.bin`; `outside-link.bin` с UNIX symlink type и содержимым `../outside.txt`. Во всех трёх случаях checker: 8/8 PASS, exit 0.

Влияние: проверка unsafe ZIP path основана на POSIX-представлении и не устанавливает переносимую безопасность/однозначность архива. Скрипт сам не извлекает ZIP: выхода записи за корень в этом опыте не было. Риск возникает при последующем извлечении другим инструментом и трактовке PASS как подтверждения безопасного пакета.

Минимальное исправление: разрешить только канонические POSIX-имена, запретить backslash/drive-prefix/NUL/алиасы и специальные типы, проверять нормализованные дубли. Различать допустимые directory entries и payload-файлы.

### IND-04 — P2: чтение и декомпрессия не ограничены

Источник: `tools/check_standard.py:34–46`.

Подтверждено кодом: `testzip()` декомпрессирует архив до проверки путей; нет лимита entries, размера отдельного файла, суммарного объёма или глубины; каталог целиком загружается `read_bytes()`.

Влияние: проверка небольшого стандарта может потреблять ресурсы большого/враждебного входа, включая файлы, которые не относятся к стандарту. Истощение ресурсов или остановка машины не воспроизводились: нагружающие тесты не нужны для установления отсутствующих границ.

Минимальное исправление: до чтения/декомпрессии проверить metadata и разумные лимиты, затем ограниченно читать и контролировать фактический объём; отклонять неожиданные payload-файлы. Не выполнять код из входного архива.

### IND-05 — P2: отсутствует состояние поставки после публикации до L5

Источники: `TESTING-LEVELS.md:60`, `templates/RELEASE.md:35`, `examples/03-release-boundary.md:11–16`.

Условие: разрешённая публикация завершилась, но L5 ещё не запускался или недоступен. Учебный пример явно описывает это промежуточное состояние; справочник допустимых статусов и шаблон выпуска перечисляют только «подготовлено», «опубликовано и проверено», «поставка неуспешна», «требуется восстановление».

Влияние: не существует точного допустимого статуса для нормальной фазы процесса. «Подготовлено» скрывает уже совершённую публикацию; «опубликовано и проверено» завышает доказательство; неуспех/восстановление могут быть ещё не установлены.

Минимальное исправление: добавить одинаковый статус «опубликовано, L5 не подтверждён» в справочник и шаблон; сохранить запрет объявлять L5 по pipeline.

## Ограничения checker и возможности улучшения

### IND-06 — P3: якоря ссылок не проверяются

Источник: `tools/check_standard.py:93`, `README.md:25`.

Воспроизведение: к путям TESTING-LEVELS.md в README добавлен `#nonexistent-section`; checker остался 8/8 PASS. Скрипт явно отбрасывает fragment, поэтому проверяет существование файла, не раздела. README называет ссылку «алгоритм», но ведёт к целому файлу.

Минимальное улучшение: направить ссылку на существующий заголовок и проверять поддерживаемые локальные anchors. Это не полный Markdown-валидатор; поддерживаемый синтаксис нужно назвать явно. Приоритет ниже IND-01: исходная документация в целом честно описывает статический характер проверки.

### IND-07 — P3: повторное чтение и пересечение нормативных формулировок

Источники: `AGENTS.md:37–45`, `TESTING-LEVELS.md:35–42`, `:64–74`, `README.md:11`, `:25`.

Подтверждено текстом: выбор TESTING-LEVELS предписан при выборе проверок, CI и выпуске; рядом многократно повторены условия доказательств и ограничения UI. AGENTS уже разрешает чтение по необходимости и переиспользование доказательств, но не определяет, когда ранее прочитанные неизменные нормативные разделы можно не читать заново.

Это возможность эффективности, а не измеренная потеря токенов. Минимальное улучшение: явно переиспользовать прочитанные актуальные правила, точечно загружать разделы при изменении риска/фазы/нормативной версии; оставить ключевые границы доступа в AGENTS. Уменьшение текста само по себе не доказывает улучшение поведения.

### IND-08 — потенциальная неоднозначность L4, не доказанный противоречивый приказ

Источники: `TESTING-LEVELS.md:12`, `AGENTS.md:45`, `templates/RELEASE.md:12`, `examples/03-release-boundary.md:9`.

Определение L4 перечисляет gates и артефакт, но не упоминает полноту актуальных требований; пример добавляет отсутствие незавершённых REQ. Общее правило AGENTS запрещает частичный результат называть полным, поэтому в совокупности строгая трактовка понятна. Для точечного чтения L4 полезно дать ссылку/короткую привязку к актуальному объёму. Не считаю это самостоятельным разрешением заявить готовность при незавершённых требованиях.

## Сохранённые механизмы

Согласованными и полезными являются независимость Light/Full от риска проверок, L1–L5 как локальная схема, отдельные статусы требований/проверок/этапов/исключений/поставки, срок и область EXC-ID, запрет автоматического переноса исключений, сохранение пользовательского diff, продолжение независимых частей при блокировке, проверка текущего состояния после смены контекста, различение сборки/UI/физического устройства/реальной интеграции, работа с невоспроизводимой исторической ошибкой и явные границы публикации. Контрольные текстовые маркеры не являются семантическим доказательством — сам rc3 это правильно оговаривает.

## Граница выводов

Не выполнялись Android/UI/production-испытания, benchmark реальных ИИ-задач, измерение качества агента, расхода токенов или стоимости. Сырые локальные воспроизведения находятся в `independent-repro.json`. Нормативный текст, шаблоны и примеры оценены вручную; выводы нельзя превращать в процент эффективности стандарта. Следующий шаг — адресные исправления и регрессионная приёмка checker, отдельный поведенческий benchmark только в согласованном охвате.
