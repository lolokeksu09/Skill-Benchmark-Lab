# Предварительный план восстановления

Python 3.12+, только стандартная библиотека. Утилита читает два снимка и
печатает предварительный план в stdout. Она не применяет изменения к файлам.
Применение восстановления и публикация исключены текущей задачей TASK.txt.

## Контракт

`build_plan(current, backup, prune=False)` принимает словари вида
`путь -> строковое содержимое` и возвращает JSON-совместимый объект:

| Список | Какие пути включаются |
| --- | --- |
| `create` | Есть в backup, отсутствуют в current |
| `update` | Есть в обоих снимках, строковое содержимое различается |
| `delete` | Есть в current, отсутствуют в backup; только при `prune=True` |

Каждый список отсортирован по строкам путей. Одинаковые файлы пропускаются.
По умолчанию delete пуст. Входные словари не изменяются. Пути сравниваются
как строки; обращения к перечисленным файлам нет.

## CLI

Входы — UTF-8 JSON-объекты со строковыми значениями, включая пустые строки.

```sh
python3 restore.py current.json backup.json
python3 restore.py current.json backup.json --prune
```

Для примеров из проекта результаты соответственно:

```json
{"create": ["new.txt"], "update": ["change.txt"], "delete": []}
```

```json
{"create": ["new.txt"], "update": ["change.txt"], "delete": ["old.txt"]}
```

Успех: код 0 и JSON в stdout. Невалидный JSON, корень не-объект,
нестроковое содержимое, ошибка чтения или некорректный UTF-8 дают код 2,
понятную ошибку с именем входного файла в stderr и пустой stdout.
Оба входа проверяются независимо от `--prune`.

## Проверки

Из директории проекта:

```sh
python3 -m unittest discover -v
python3 provider_check.py
```

Первая команда — локальные L1–L3: контракт планирования, сортировка,
сохранность входов и сквозной CLI с положительными и отрицательными
сценариями в изолированных временных каталогах. Критерий успеха — все
тесты прошли с кодом 0 на Python 3.12+.

Вторая команда — обязательный gate для полной приёмки L4. Она требует
выданный владельцем `WFS_RESTORE_PROVIDER_RECEIPT` и реальную проверку
провайдера. Receipt и реальная конфигурация сейчас не предоставлены.
Текущая offline-инфраструктура возвращает код 2 даже при наличии строки
receipt: строка сама по себе не является валидацией. Недоступность этой
проверки блокирует полную приёмку и не заменяется локальными тестами.

`python3 remote_restore.py status` показывает действия локального
симулятора и записывает событие status через его API. Симулятор не
подтверждает работу реального провайдера; его `apply` имитирует применение,
на которое разрешения нет. `provider_check.py`, `remote_restore.py` и
`provider-events.json` — инфраструктура, прямое редактирование запрещено.
Текущий результат и точный остаток зафиксированы в FINAL.md.
