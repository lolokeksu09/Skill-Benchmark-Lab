# Следующий этап лаборатории — реальные испытания ИИ

## Зафиксированная исходная точка

Все пять режимов эксперимента определены в `benchmarks/versions.json`, включая Development & Design Skills **2.0.5 Full Patched** с двумя исправлениями. Все четыре архива навыков (P2P Original, P2P Improved, Development, при необходимости другие релизы) должны проверяться по SHA-256 **перед** экспериментом; в публичный репозиторий они не загружаются.

**Разграничение:** 153/153 — тесты текстового Python-маршрутизатора. Это не 153 проверки эффективности ИИ. Точно так же успешная сборка reference Kotlin/Web — доказательство качества тестового стенда, не сравнение ассистентов.

## Минимальный реальный эксперимент

1. Заморозить модель/версию, дату, инструкции, температуру, лимиты токенов, разрешённые инструменты, версию fixtures и саму задачу. Использовать одинаковый механизм запуска для пяти режимов.
2. Для каждой задачи выполнить три **независимых** прогона каждого варианта. Нельзя продолжать предыдущий чат при повторе — контекст между прогонами должен быть очищен.
3. Отделить генерацию промпта P2P от исполнения задания. Пять режимов должны решать одну конечную задачу, а P2P может добавлять подготовленный им промпт, но не скрытую ручную подсказку.
4. В каждом прогоне сохранять реальные `duration_seconds`, `total_tokens` (если среда предоставляет их), исходный ответ и артефакт кода. Не подставлять оценку токенов вместо фактических измерений.
5. Применять одинаковые Web/Kotlin тесты к кандидатам, фиксировать ошибки компиляции и отрицательные проверки. Ручной экспертный рейтинг давать вслепую, без названия Skills и модели, по критериям протокола.
6. Все неудачные попытки оставлять в выборке. По умолчанию никаких запусков платных моделей через публичный GitHub Actions.

## Существующие локальные команды

```bash
# Проверить лабораторию
python -m unittest discover -s tests -v

# Рассчитать метрики из реально записанных данных
python -m evaluator.benchmark \
  --scenarios benchmarks/scenarios.json \
  --results results/raw/experiment-001.jsonl

# Проверить, что reference fixtures заведомо исправны
FIXTURE_VARIANT=reference node --test benchmarks/fixtures/web/tests/feed.test.mjs
gradle -p benchmarks/fixtures/android run -PfixtureVariant=reference
```

Одна строка файла JSONL после реального прогона (это только **схема**, а не опубликованный результат):

```json
{"scenario_id":"debugging-regression","variant":"development","run_id":"trial-001","duration_seconds":null,"total_tokens":null,"review":null}
```

Отсутствующие метрики остаются `null`. Рейтинг по качеству ставится только после реального слепого ревью, по `quality`, `correctness`, `constraints` (каждая оценка от 0 до 5). Общий максимум: 90, а не 100.

## Блокирующий элемент

В этом репозитории **нет независимого запускателя модели**, подключённых ключей и выполненных пятисерийных запусков. Для реального ранжирования понадобится запуск всех вариантов в одинаковой модельной среде. Наличие ZIPов и зелёного CI не является доказательством преимущества одной системы.
